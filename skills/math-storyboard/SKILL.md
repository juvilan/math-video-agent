# 수학 영상 콘티 — 같이 만든다

**코드보다 먼저 온다.** 기획 없이 만든 애니메이션은 예쁘지만
아무것도 가르치지 못한다.

그리고 **혼자 만들지 않는다.** 완성된 기획안을 통째로 들이밀고
"괜찮으세요?"라고 물으면 사용자는 고칠 데를 못 찾거나, 찾아도
전부 다시 만들어야 한다. 여섯 단계로 쪼개서 되돌리기를 싸게 만든다.

---

## 먼저 — 의도 카드를 읽는다

프로젝트에 `.mv/intent.md` 가 있으면 **묻기 전에 읽는다.**
톤·대상·길이·색·금지 목록이 이미 적혀 있으면 그건 묻지 않는다.
**이미 정해진 걸 다시 묻는 것도 의도를 무시하는 것이다.**

없으면 `manim-video` 스킬의
`templates/project/intent.md` 를 복사해 만들고, 아래 1~2단계에서
최소한만 채운다. 나머지는 만들면서 드러나는 대로 채운다.

## 게이트는 세 곳

`math-video-director` 가 멈추는 지점은 셋이고, 그중 **G1이 이
스킬의 담당**이다.

```
G1 방향   ← 여기         한 문장 · 대상 · 길이 · 비트 순서
G2 그림                  비트별 실제 렌더 스틸 판
G3 첫 씬                 씬 1 완성본
```

아래 0~5단계는 G1 안에서 도는 흐름이다. 3단계(비트 뼈대)까지
확인받으면 G1이 닫히고 코딩으로 넘어간다. **4~5단계(콘티 스케치,
내레이션)는 G2에서 실제 스틸로 대체되므로, 급하면 건너뛰고
바로 스틸을 뽑는 편이 낫다** — 텍스트 스케치보다 진짜 그림이
언제나 정확하다.

## 협업 원칙

1. **한 번에 한 단계.** 다음 단계를 미리 만들어두지 않는다.
2. **빈칸을 내밀지 말고 후보를 낸다.** "대상이 누구예요?"보다
   "고2 미적분 이수자 / 중3 / 일반인 — 어느 쪽인가요?"가 낫다.
   사용자가 타이핑할 일을 줄인다. `AskUserQuestion`을 쓴다.
3. **각 단계 끝에서 멈춘다.** 승인 없이 다음으로 넘어가지 않는다.
4. **되돌리기를 흡수한다.** 3단계에서 "이 비트 빼자"가 나오면
   그 단계만 고치고, 이미 만든 뒷단계 중 영향받는 것만 갱신한다.
   전부 다시 만들지 않는다.
5. **"알아서 해줘"는 존중한다.** 그러면 기본값으로 진행하되,
   각 게이트에서 **결과를 보여주고** 넘어간다. 조용히 6단계까지
   가버리지 않는다.

## 0단계 — 재료 받기

사용자가 준 것을 먼저 확인한다.

- 주제 한 줄만 있는가
- 교과서/논문 스크린샷, 수식 이미지가 있는가 → **LaTeX로 받아쓴다**
  (아래 "수식 이미지" 절)
- 기존 수업 자료, 학습지, 판서 사진이 있는가
- 참고하고 싶은 영상이 있는가

없으면 그냥 다음으로 간다. 재료를 캐묻느라 시작을 늦추지 않는다.

---

## 1단계 — 핵심 한 문장 <sub>게이트</sub>

전체 영상이 전달하는 사실을 **한 문장**으로 못 쓰면 주제가 너무
크다는 뜻이다.

```
✗ "선형대수에 대하여"                  ← 주제지 문장이 아님
✗ "행렬식과 고유값과 대각화"            ← 세 편짜리
✓ "행렬식은 그 변환이 넓이를 몇 배로 만드는지를 나타내는 수다"
```

**후보 2~3개를 각도를 달리해서 낸다.** 같은 주제라도 어디를
찌르냐에 따라 완전히 다른 영상이 된다.

> 예 — 주제 "미분"
>
> | 후보 | 문장 | 영상의 성격 |
> |---|---|---|
> | A | 미분은 곡선을 아주 가까이서 보면 직선이라는 사실이다 | 직관·기하 |
> | B | 미분은 "지금 이 순간 얼마나 빨리 변하는가"를 재는 도구다 | 물리·응용 |
> | C | 미분과 적분은 서로를 되돌린다 | 구조·미적분학 기본정리 |

`AskUserQuestion`으로 고르게 하고, 사용자가 문장을 고쳐 쓰면
그대로 받는다.

**여기서 멈춘다.**

---

## 2단계 — 대상·길이·톤 <sub>게이트</sub>

한 번에 묶어서 묻는다. 세 번 나눠 묻지 않는다.

| 항목 | 기본값 | 왜 중요한가 |
|---|---|---|
| 대상 | 고1~고2 | **이게 제일 크게 갈린다.** "미분을 아는 사람"과 "미분을 처음 보는 사람"은 완전히 다른 영상이다 |
| 전제 지식 | 대상에서 따라옴 | 어디서부터 설명을 시작할지 |
| 길이 | 5분 | 3~10분이 스위트스팟 |
| 톤 | 왜 그런가 중심 | vs 문제풀이 중심, vs 시험 대비 |
| 언어 | 한국어 | 영어 버전 필요 여부 |

대상만은 반드시 확인한다. 나머지는 기본값으로 가도 크게 안 틀린다.

**여기서 멈춘다.**

---

## 3단계 — 비트 뼈대 <sub>게이트</sub>

**제목만.** 내레이션도 화면 설계도 아직 안 쓴다. 지금은 순서가
맞는지만 본다. 순서가 틀렸는데 내레이션까지 써놓으면 버리는 게
많아진다.

기본 5단 구조 (주제에 따라 ④를 빼거나 ②를 둘로 늘린다):

```
① 훅        구체적인 질문/현상 하나              10~20s
② 직관      계산 없이 그림으로만 이해시킨다       60~120s
③ 형식화    그 그림에 기호를 붙인다               60~90s
④ 확장      일반화 / 놀라운 따름정리              60~120s
⑤ 여운      더 큰 그림 한 줄                      15~30s
```

**절대 규칙: 그림이 기호보다 먼저 온다.**
정의 → 정리 → 증명 순서는 교과서지 영상이 아니다.

이렇게 내민다:

```
1. 훅       — 종이를 반으로 42번 접으면 달에 닿는다             15s
2. 직관     — 접을 때마다 두께가 두 배가 되는 걸 눈으로 본다     50s
3. 형식화   — 그 "두 배씩"에 2^n 이라는 이름을 붙인다           60s
4. 확장     — 그래서 지수함수는 어떤 다항식보다도 빨리 자란다    70s
5. 여운     — 복리, 전염, 무어의 법칙이 전부 같은 모양이다       20s
                                                    합계 215s
```

물어볼 것: **빠진 비트 / 뺄 비트 / 순서**. 비트마다
"이게 없으면 뭐가 안 되는가"에 답할 수 있어야 한다.

**여기서 멈춘다.**

---

## 4단계 — 콘티 (화면 설계) <sub>게이트</sub>

비트마다 **화면에 뭐가 보이고 뭐가 움직이는지**를 그린다.
글로만 쓰면 코드로 옮길 때 해석이 갈리므로 텍스트 스케치를
함께 그린다.

```
┌─ 비트 2 · 직관 ───────────────────── 50s ─┐
│                                            │
│              ▁▂▃▅▇                         │
│           (막대가 두 배씩)                  │
│                                            │
│   1  2  4  8  16  32 …                     │
│   ───────────────────────  접은 횟수        │
│                                            │
│   [자막] 접을 때마다 두께가 두 배            │
└────────────────────────────────────────────┘

움직임: 막대가 왼쪽부터 하나씩 솟아오름 (LaggedStart)
        높이 라벨이 막대를 따라 올라감
색:     막대 BLUE_B → 마지막 막대만 YELLOW
```

한 비트에 하나씩. 다 그린 뒤 한꺼번에 보여주지 말고,
**비트 순서대로 그려가며** 사용자가 중간에 끊을 수 있게 한다.

이 단계에서 같이 정하는 것:

- **색 매핑** — 변수 하나 = 색 하나. 동시에 3~4색을 넘기지 않는다
- **화면 구성 규칙** — "수식은 위, 그림은 아래" 같은 것. 씬 내내 유지
- **자막 위치** — 기본은 하단. 그림이 아래로 내려오는 비트는 미리 표시
- **Scene 이름과 시작 템플릿**

| 화면 유형 | 템플릿 |
|---|---|
| 수식을 항별로 해설 | `formula_walkthrough.py` |
| 수식 A → B 변형 | `transform_anagram.py` |
| 함수 그래프·접선·적분 | `graph_plot.py` |
| 벡터장·선형변환 | `vector_field.py` |
| ODE·물리 궤적·3D | `ode_trajectory.py` |
| 그 외 | `scene_base.py` |

**여기서 멈춘다.**

---

## 5단계 — 내레이션 <sub>게이트</sub>

이제 **실제로 읽을 문장**을 쓴다. 요약이 아니라 대본이다.

순서를 지킨다:

1. 비트마다 말로 할 내용을 문장으로 쓴다
2. 길이를 계산한다 — **한국어 글자 수 ÷ 5.5 ≈ 초** (차분한 설명 톤)
3. 3단계에서 잡은 길이와 맞는지 본다. 안 맞으면 **문장을 고치거나
   길이를 고친다.** 둘 중 뭘 고칠지는 사용자에게 묻는다

자막은 내레이션 전문이 아니라 **핵심 구절**만 뽑는다. 전문을
깔면 시청자가 읽느라 화면을 안 본다.

```
내레이션: "종이 한 장의 두께는 0.1밀리미터입니다. 그런데 이걸
          반으로 접으면 0.2밀리미터가 되죠. 한 번 더 접으면 0.4."
          (63자 → 약 11.5초)
자막:     "접을 때마다 두 배"
```

**여기서 멈춘다.**

## 6단계 — 확정

`templates/storyboard.md` 형식으로 파일에 저장한다.
마지막에 체크리스트를 **실제로 대조해서** 결과를 적는다.

```
□ 핵심 한 문장이 쓰여 있다
□ 모든 비트에 "없으면 뭐가 안 되는지"의 답이 있다
□ 그림이 기호보다 먼저 나온다
□ 내레이션이 실제 문장이다 (요약 아님)
□ 길이 합계가 목표의 ±20% 안이다
□ 비트마다 콘티 스케치가 있다
□ 씬 이름과 템플릿이 지정돼 있다
□ 색 매핑이 정해졌고 3~4색을 넘지 않는다
□ 한 화면에 수식 3개 이상인 비트가 없다
□ 5초 넘게 정적인 비트가 없다
```

여기까지 나오면 `manim-video` 스킬이 받아서 코드로 옮긴다.
**단, 다음은 곧바로 완성 씬이 아니라 G2 — 비트별 정지 화면만
만들어 스틸 판으로 확인받는 단계다.** 텍스트로 합의한 그림과
실제 렌더는 다르다.

렌더가 끝나면 `math-video-qc`가 이 문서를 다시 꺼내서 **기획 대비
실제**를 대조한다. 그러니 비트별 목표 길이를 꼭 적어둔다.

그리고 영상이 끝나면 이번에 드러난 선호를 `.mv/intent.md` 로
올린다. 특히 "이건 아닌데"가 나온 것은 **하지 말 것** 목록에.

## 수식 이미지 → LaTeX

교과서·논문 스크린샷을 주면 LaTeX로 받아쓴다.
(원본 워크플로우의 Mathpix 자리를 대신한다.)

받아쓸 때 **항을 나눠서** 쓴다. `manim-video`가 그대로
`MathTex(...)` 인자로 넘길 수 있어야 한다.

```python
# 이미지: dx/dt = σ(y − x)
MathTex(r"\frac{dx}{dt}", "=", r"\sigma", "(", "y", "-", "x", ")")
```

통짜 문자열로 주면 색칠도 변형 애니메이션도 안 된다.

받아쓴 뒤에는 **원본 이미지와 대조해 확인받는다.** 첨자나 괄호
범위를 잘못 읽으면 영상 전체가 틀린 식으로 나간다.

---

## 사용자가 급할 때

"빨리 하나 만들어줘" 류의 요청이면 1~5단계를 **한 번에 초안으로
내되**, 어디를 고치면 되는지 명시한다.

```
초안입니다. 아래 중 하나만 말씀해주시면 그 단계부터 다시 갑니다.
  · 핵심 문장이 다르다        → 1단계
  · 대상/길이가 다르다        → 2단계
  · 비트 순서가 다르다        → 3단계
  · 화면 구성이 다르다        → 4단계
  · 말투/문장이 다르다        → 5단계
```

단계를 건너뛰는 것과 단계가 없는 것은 다르다. 급해도 구조는 남긴다.
